Case Study · Fisec Global

Intelli-Hire

Recruiters were reading every resume by hand and reaching inconsistent conclusions. Intelli-Hire ranks candidates against a job description and makes the whole pipeline searchable — without handing the decision to a model.

— the shortlist, not the verdict
Role Frontend Architecture & UI
Company Fisec Global
Timeline Aug 2025 – Present
Focus Micro-frontends & access control

The problem

Screening was entirely manual. Every application was read by a person, which made the early pipeline the slowest part of hiring and meant the same candidate could be assessed differently depending on who opened the file and how many they had already read that day.

Resumes also had nowhere to live. Once a role closed, its applicants were effectively lost — a strong candidate for a future opening sat unreachable in a folder, so sourcing started from zero each time.

The line I held

The system produces a ranked shortlist, not a decision. Recruiters still choose — the product's job is to make the first pass fast and consistent, and to show why a candidate surfaced.

Approach

  • Rank, don't filter — matching orders candidates by fit against the job description rather than silently discarding anyone, so a recruiter can always look further down the list.
  • Make the pipeline searchable — structured candidate profiles in a database with advanced filters, so past applicants stay findable for future roles.
  • Control who sees what — resumes are sensitive personal data, so role-based permissions and access controls were part of the design, not a later addition.
  • Modular frontend — a micro-frontend architecture so the admin, recruiter, and dashboard surfaces can evolve independently.

Decisions worth explaining

Micro-frontends for the application shell

The recruiter workspace, admin controls, and analytics dashboards are separate frontend modules composed into one application.

Trade-off: more build and integration complexity than a single bundle. Lets each surface ship on its own schedule without a change to admin risking the recruiter's daily workflow.

Role-based auth with admin controls from the start

Permissions were modelled before features were built on top of them, with admin tooling for managing who holds which role.

Trade-off: upfront design work before any visible feature. Retrofitting authorization onto a live system holding personal data is how access-control bugs happen.

Matching surfaces its reasoning

A ranked candidate is shown with the signals behind the score rather than a bare number, so a recruiter can judge whether the match is meaningful.

Trade-off: a busier results view than a single percentage. An unexplained score is either trusted blindly or ignored entirely — both are worse than a slightly denser row.

Access tracking on resume views

Resume access is controlled and recruiter activity is recorded, so engagement with candidate data is auditable.

Trade-off: extra write traffic and a feature no user asks for. Necessary for anything handling other people's personal information.

What I built

  • A role-based authentication system with admin controls, improving user management and platform security.
  • An AI-powered resume matching system that ranks candidates against a job description.
  • A searchable resume database with advanced filters and structured candidate profiles.
  • Resume access controls and analytics tracking recruiter activity and engagement.
  • A modular frontend architecture using micro-frontends, with interactive dashboards and data visualizations.

Outcome

Manual screening time dropped substantially: recruiters open a ranked shortlist instead of an unordered pile, and the resume database means a candidate who was strong but wrong-timed can be found again when a fitting role opens.
