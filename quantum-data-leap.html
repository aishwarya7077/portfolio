Case Study · Fisec Global

Quantum Data Leap

A data-intensive platform that clients found hard to navigate, rebuilt around a reusable component library and dashboards designed so the important number is the one you see first.

— density is fine; confusion isn't
Role UI/UX Design & Frontend
Company Fisec Global
Timeline Aug 2025 – Present
Focus Design systems & data visualization

The problem

The platform handled genuinely complex, data-intensive operations. The data was all there and the calculations were correct — but clients struggled to navigate it and, more importantly, struggled to act on it. Screens presented everything at once with no visual hierarchy, so the critical number and an incidental one carried the same weight.

Underneath that sat a second problem: the interface had no shared vocabulary. Similar controls had been built more than once in slightly different ways, spacing and type sizes varied between screens, and every new feature meant re-deciding basics that should already have been settled. Inconsistency slowed the team down and made the product feel unreliable to users.

The real brief

Not "make it prettier" — make a dense operational tool legible, and give the team a system so it stays that way as the product grows.

Approach

I started before the pixels: collecting requirements from cross-functional stakeholders, working through the business logic, and turning data use cases into flows. Understanding which question a screen exists to answer is what makes it possible to decide what deserves prominence.

  • User journeys and information architecture — mapping how someone actually moves through the data, then restructuring navigation to match that rather than mirroring the backend's shape.
  • Low-fidelity design first — resolving layout and hierarchy in wireframes, where changes are cheap and the conversation stays about structure instead of colour.
  • A component library — typography scale, spacing system, and layout patterns defined once and reused, so consistency is the default rather than an act of discipline.
  • Responsive and accessible by construction — built into each component as it was written, not retrofitted per screen.

Decisions worth explaining

A component library before feature work

Rather than styling screens one at a time, I established the primitives first — type scale, spacing, and the shared layout patterns — and built features from them.

Trade-off: slower for the first two screens. Everything after them got faster, and consistency stopped depending on whoever happened to be building.

Hierarchy over completeness

Dashboards lead with the number that drives a decision and demote supporting detail to a second read, instead of giving every metric equal visual weight.

Trade-off: some users have to click once more for a secondary figure. Worth it — a screen where everything is emphasised communicates nothing.

Charts chosen for the question, not the effect

Each visualization was picked for the comparison it needs to support — magnitude, trend, or proportion — with axes and labelling kept plain.

Trade-off: less visually striking than the dense, decorative dashboards that demo well. Considerably more useful at 9am on a working Tuesday.

Accessibility as part of the component contract

Keyboard paths, focus states, contrast ratios, and screen-reader semantics were handled inside each component when it was written.

Trade-off: more work per component upfront. Cheaper by a wide margin than auditing and patching dozens of screens later — and it holds as the product grows.

What I built

  • A reusable UI component library with an established typography scale, spacing system, and layout patterns used across the application.
  • User journeys, information architecture, and low-fidelity designs that improved visibility and navigation across the data screens.
  • Accessible dashboards with data visualizations, built so density never comes at the cost of legibility.
  • Responsive layouts delivering a coherent experience across desktop and mobile, rather than a desktop tool awkwardly squeezed onto a phone.
  • Interfaces aligned with product design principles and industry practice, which lifted overall usability and visual consistency.

Outcome

The component library is now the shared foundation for the product's desktop and mobile views. New screens start from established patterns instead of a blank file, which keeps the interface consistent as the product grows and removes a class of decisions from every feature.
